> This page covers the **merge-queue variant** (`docs/variants/evidence-gate.yml`, `docs/variants/ruleset-merge-queue.json`). For land on evidence, the variant `main` runs, read `LAND.md`. Key generation and the policy are the same for both; `README.md` has the commands.

# Repository settings and setup

What to commit, what to turn on, and what each setting is for. Everything here uses features that ship today. Steps marked "not run on GitHub" have only been exercised locally.

## 1. Files to commit

| File | What it is |
| --- | --- |
| `.github/workflows/evidence-gate.yml` (copy it from this directory) | The workflow: verify the PR head's evidence, skip tests if it verifies, always run them in the merge queue. |
| `.cilock/policy.rego` | The rule: tests exited 0, the command is exactly your test command, at least one package printed `ok`, none printed "no tests to run". |
| `.cilock/policy.json` | The unsigned policy (generated by `make-policy.sh`), one step named `test`, trusting the agent key. |
| `.cilock/policy.signed.json` | The same policy signed with the policy key. |
| `.cilock/policy.pub` | The policy key's public half. CI uses it to check the policy signature. |

The workflow reads the last three from the pull request's base commit, never from the PR. A change to the policy has to land first, through review, before it can affect any other PR. The first PR that adds these files runs the full tests, because the base has no policy yet.

## 2. Keys (two, kept apart)

```sh
# Agent key: signs test evidence. Every agent that may produce evidence holds a copy.
mkdir -p ~/.config/cilock
openssl ecparam -name prime256v1 -genkey -noout -out ~/.config/cilock/agent.key
openssl ec -in ~/.config/cilock/agent.key -pubout -out agent.pub

# Policy key: signs the policy. A human holds it. Agents never do.
openssl ecparam -name prime256v1 -genkey -noout -out policy.key
openssl ec -in policy.key -pubout -out .cilock/policy.pub
```

Build and sign the policy (`make-policy.sh` and `policy.rego` are in `.cilock/`; edit the rego to your test command first):

```sh
./.cilock/make-policy.sh agent.pub .cilock/policy.json          # step name defaults to "test"
cilock policy validate -p .cilock/policy.json
cilock sign -k policy.key -f .cilock/policy.json -o .cilock/policy.signed.json
```

Expiry: `make-policy.sh` sets `expires` one year out. A policy past `expires` fails every verify, and CI then runs the tests, so an expired policy costs money but never lets a bad merge through. Re-sign it before then.

What a file key proves: someone holding this key ran this command on this commit. It does not say which agent, or on what machine. Rotating the agent key means regenerating the policy with the new public key and landing it.

## 3. Ruleset (`ruleset-merge-queue.json`, next to this file)

```sh
gh api repos/OWNER/REPO/rulesets --method POST --input docs/variants/ruleset-merge-queue.json     # not run on GitHub
gh repo edit OWNER/REPO --enable-auto-merge                              # lets `gh pr merge --auto` work
```

What it sets on the default branch:

- **Pull request required**, one approval, stale approvals dismissed on push. Change the count to taste.
- **Required status check `ci`**. This is the aggregator job in the workflow, the only check you require. The `test` and `admit` jobs are not required on their own: `test` is legitimately skipped when evidence admits the PR, and `ci` is the job that knows when a skip is allowed.
- **Merge queue**, `SQUASH`, `grouping_strategy: HEADGREEN`. HEADGREEN merges every entry ahead of a passing group, because that group's run tested their combined tree. That is sound here only because the workflow runs the full suite on every `merge_group` event. Use `ALLGREEN` if you would rather every entry pass its own build.
- No bypass actors. Do not add one for agents.

The ruleset JSON follows the shape of a live merge-queue ruleset read from GitHub's API (`merge_queue` and `required_status_checks` parameters). The `deletion` and `non_fast_forward` rules are standard GitHub rule types that were not in that read.

If you keep no merge queue, delete the `merge_queue` rule and the `merge_group` trigger. Then no commit is ever tested after merge except by the PR's own run. Expect a green PR to turn main red when two changes interact. The post's argument for the queue is exactly that.

## 4. Permissions, secrets, variables

- Workflow `permissions: contents: read`. Nothing else. The file-key path needs no `id-token: write`.
- Secrets: none. Variables: none.
- Agents need write access to push branches and the two ref namespaces `refs/evidence/*`, `refs/claims/*` and (land on evidence) `refs/locks/*`. The ruleset above targets the default branch only, so these refs are not blocked. Not run on GitHub: that GitHub accepts pushes to those namespaces on your repo (it accepts refs under `refs/` generally; confirm once).
- Fork PRs: evidence lives in the base repository, so a fork PR never finds any and always runs the tests. That is the safe direction.
- Housekeeping: delete a PR's evidence ref after merge (`git push origin --delete refs/evidence/<sha>`) or sweep old ones on a schedule. Nothing in this kit does that for you.
- Pin the action SHAs and the `cilock` hash as the workflow does. To move to a newer cilock, read `https://cilock.dev/dl/manifest.json` and change both `CILOCK_VERSION` and `CILOCK_SHA256`.

## 4a. The GitHub Action (`aflock-ai/cilock-action`) and this kit

The action wraps a command and signs it, which is the producer half. It has no verify input. The only verify path is the `cilock verify` CLI, which this workflow installs and runs. The documented action pin (`v1.0.4`, commit `d39bb9b17e392520f9e7eef17cf355c027a5c283`) records the older `command-run/v0.1` and, per its reference page, cannot satisfy this policy's `command-run/v0.2` type. If you want the fallback `test` job to also produce CI-signed evidence, run `cilock run` in that job with the CLI instead. This kit does not do that.

## 5. If you use the TestifySec Platform and Pushgate (keyless agent identity)

This replaces the file key and the evidence ref with a platform-issued agent identity and the platform's evidence store. Nothing in this section was run for this kit. Each item is taken from the cilock reference docs, the `cilock` v4.10.0 help, or the workflow in `testifysec/dagger-pushgate-demo`.

Platform side:

1. A human enrolls each agent machine: `cilock enroll agent`. A person approves it in the browser with a second factor. The identity is time-bound (8 hours by default) and cannot be extended. An agent can start the command but cannot approve it.
2. Connect the repository to the TestifySec Platform, then register the repo's Actions to read evidence, as a tenant admin after `cilock login`: `cilock trust github OWNER/REPO --scope attestation:read`. This needs no stored secret. CI authenticates to Archivista with the job's GitHub OIDC token.
3. Write the policy with the scaffold, which copies the agent functionary from the enrolled identity: `cilock policy template --goal tests`, fill the `__FILL__` slots (the pinned test argv, for example `["go","test","./..."]`), `cilock policy validate -p .pushgate/policy.json`. A human signs it: `cilock sign --human -f .pushgate/policy.json -o .pushgate/policy.signed.json`. `cilock policy prove -p .pushgate/policy.json` tests the policy locally against a passing and a failing run.
4. For Pushgate, assign that policy to the repository in Block mode in the Pushgate settings and have agents push through it (`cilock pushgate connect` redeems the setup link). Pushgate then refuses a push without passing evidence. `cilock pushgate status --commit <sha>` says whether Pushgate accepted a commit.

Workflow changes for this path:

- Add `permissions: id-token: write` to the `admit` job.
- Replace the evidence-ref fetch and the `verify` flags with the Archivista lookup used in the demo repository's `c-pushgate.yml`:
  `cilock verify -p admission.json --subjects "sha1:${HEAD_SHA}" --policy-emails "<human signer email>" --policy-fulcio-oidc-issuer https://platform.testifysec.com/fulcio/oidc --enable-archivista --archivista-oidc --format json`
  with `admission.json` being the signed policy read from the base commit.
- Agents run `cilock run --step tests -a test-results -- <argv>` as `cilock policy guide --goal tests` prints it, with `--platform-url` pointing at your platform and no `-k`.

Known blocker as of the post: the demo repository's CI skip ran once and failed closed (it ran the full suite) because the platform refused the workflow's read of the verdict. The fix was in review at the time. Do not publish timings for the platform path until that run completes.

## 6. What cannot be done with shipped features

- **Verifying that the agent ran on a clean tree.** The git attestor records the commit and tree hash, not the working-tree status (`status` is null in the recorded evidence). An agent that commits, edits a file without committing, and tests that, produces evidence for the commit that does not describe what ran. Step 3 of the skill tells agents to refuse that; nothing enforces it. A fresh worktree per run reduces the risk, not to zero.
- **Proving which agent signed, with a file key.** Use the platform's enrolled agent identity for that.
- **Evidence that survives a rebase.** Evidence names a commit. A rebase makes a new commit and needs a new run. The post's input-digest variant needs the `dagger` attestor and is not part of this kit.
- **Skipping the merge-queue run.** By design the queue runs the full suite once.
